# 发布与更新策略

## 仓库结构

首个稳定版采用单仓库、单镜像：后端、WebUI、内置字幕源适配器、数据库迁移和部署
文件一起版本化。这样可以保证每个版本内部兼容，也让 NAS 用户只更新一个镜像。

Provider Adapter 仍保持清晰的代码接口，但短期不拆分仓库、不提供插件市场。

## 版本归属

- 拾幕使用语义化版本号，例如 `0.7.1`。
- 每个内置适配器保留接口版本，用于诊断和问题定位。
- Subliminal、ffsubsync 等依赖版本由 `uv.lock` 固定，随主镜像更新。
- 配置版本和数据库版本用于启动时迁移，不是用户需要单独安装的组件。

## GitHub 自动化

每次提交运行代码检查和自动测试。创建版本标签后，发布流程构建
`linux/amd64`、`linux/arm64` 镜像并推送到 GHCR。发布说明来自中文更新日志。

## 用户更新

第一版只提供整镜像更新，不在 WebUI 中直接替换正在运行的容器：

```bash
docker compose pull
docker compose up -d
```

WebUI 可以检查版本并显示更新地址。由 NAS 的 Docker 管理器执行升级更透明，也更
容易回滚。升级前建议备份 `/appdata/config.yaml` 和 `/appdata/data`。

## 数据与回滚

配置、SQLite 数据库和运行元数据都保存在 `/appdata`。数据库结构通过版本化迁移
向前升级。回滚时应同时恢复旧镜像和升级前的数据备份，避免旧程序读取新结构。
